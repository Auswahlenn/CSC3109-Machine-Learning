\section{Introduction}

\subsection{Background and Motivation}
Earth-observation satellites, aerial surveys, and high-resolution basemaps now produce far more imagery than analysts can review by hand \cite{Zhu2017}. Getting useful information out of that imagery like where infrastructure is located, how an area is changing, matters for urban planning, environmental monitoring, infrastructure management, and disaster response, among other applications. Scene classification, labelling an image patch with a land-use category, is the basic task that most of this depends on.

Until the early 2010s this problem was tackled with handcrafted features: colour histograms, texture descriptors, SIFT-based bag-of-visual-words. These worked reasonably well for coarse distinctions but stalled because they describe low-level appearance rather than the structure of a scene. Deep convolutional networks changed that by learning features directly from data instead of relying on hand-designed ones. Since AlexNet's ImageNet result \cite{Krizhevsky2012}, they have taken over image classification generally, and the remote-sensing literature shows the same pattern: deep models are now standard on aerial scene classification benchmarks \cite{Cheng2020}.

The dataset used in this project makes the task harder in two specific ways. First, the four classes --- \texttt{coastal\_mansion}, \texttt{dense\_residential}, \texttt{nursing\_home}, and \texttt{sparse\_residential} --- all look visually similar to each other when seen from above. What separates them is density and spatial arrangement rather than distinct objects or colours, so a model has to pick up on layout, not just presence of things. Second, there are only 700 training images per class, which is little enough that a network trained from scratch would likely overfit. This is why data augmentation and transfer learning from pre-trained models are central to our approach rather than optional extras.

We also cared about two things beyond accuracy. One is fair comparison:
architecture papers are often hard to compare because they differ in data
splits, augmentation, training budgets, or evaluation setup, so we fixed those
factors across our experiments and documented the few architecture-specific
differences (preprocessing, effective backbone resolution, and the custom
CNN's learning-rate schedule). The other is deployment; a model is only useful
if it can actually be run somewhere. So we packaged the best-performing model
as a containerized inference service rather than leaving it as a notebook
result.

\subsection{Problem Statement}
Each team in this cohort is assigned a partition of a 38-category aerial-imagery benchmark. The class names, the 800 images per class, and the native $256 \times 256$ pixel resolution identify the source as \textbf{PatternNet}, a high-resolution dataset collected mainly over US cities from Google Earth and Google Map API imagery. Our partition (\emph{set 23}) contains four categories:
\begin{center}
\texttt{coastal\_mansion}, \quad \texttt{dense\_residential}, \quad
\texttt{nursing\_home}, \quad \texttt{sparse\_residential},
\end{center}
each with 700 training images and 100 held-out validation images. The held-out
images never appear in training and are used only for final evaluation.

The task is standard four-way image classification: train a model that takes a
$256 \times 256$ RGB aerial image and outputs a probability for each of the
four classes, and evaluate it on the held-out set using accuracy, per-class
and macro-averaged precision, recall, and $F_1$-score, and the confusion
matrix.

What makes this partition hard is that all four categories are residential or
institutional building scenes. A nursing home is essentially a large
residential complex; dense and sparse residential areas differ in lot size and
building spacing rather than in kind; the most reliable cue for a coastal
mansion is the shoreline next to it, not the building itself. So the classes
look alike (same mix of buildings, roads, and vegetation) while images within
a class vary a lot (roof colour, vegetation cover, season, layout).

The project specification adds three practical requirements: (i) the team must
investigate at least as many deep learning approaches as it has members
(five); (ii) every open-source library used must be registered and justified,
and our own contributions documented; and (iii) the best model must be
deployed in a container that accepts an aerial image and returns a predicted
label with confidence scores.

\subsection{Project Objectives}
We set ourselves six objectives:

\begin{enumerate}
  \item \textbf{O1: Understand the data.} Explore class balance, image
  statistics, and visual overlap between categories, and use the findings to
  justify pre-processing and augmentation choices.
  \item \textbf{O2: Evaluate without leakage.} Use a shared data pipeline
  with a fixed internal tuning split for development and checkpoint selection,
  and touch the 400 held-out images only once, for final evaluation.
  \item \textbf{O3: Investigate five approaches.} One per team member: a
  from-scratch CNN baseline, three pretrained CNN families (ResNet-50,
  EfficientNet-B0, MobileNetV2), and a vision transformer.
  \item \textbf{O4: Compare fairly.} Train every model with the same seed,
  dataset split, raw input size, augmentation, batch size, epoch budget, and
  early-stopping patience, while explicitly documenting necessary
  architecture-specific preprocessing and optimisation choices.
  \item \textbf{O5: Maximise held-out performance.} Get the best accuracy
  and macro-$F_1$ we can, and use confusion matrices to understand the
  remaining errors.
  \item \textbf{O6: Deploy the best model.} Package it in a Docker
  container with a web interface that returns the predicted category and
  confidence scores, with automated contract tests covering the shared data
  pipeline and training entrypoint.
\end{enumerate}

\subsection{Review of Existing Approaches}
\label{sec:review}

\subsubsection{From Handcrafted Descriptors to Learned Features}

Early remote-sensing scene classification relied on handcrafted descriptors ---
colour histograms, texture measures, and SIFT-based bag-of-visual-words
representations. These encode low-level appearance and therefore struggle
precisely where our partition is hardest: distinguishing categories that share
the same visual vocabulary and differ only in spatial arrangement. The shift to
learned representations after AlexNet \cite{Krizhevsky2012} resolved this by
inferring features directly from data, and the remote-sensing literature has
followed the same trajectory \cite{Zhu2017, Cheng2020}.

The magnitude of the improvement is well documented. In an aerial forest
segmentation experiment, Kwenda et al. \cite{Kwenda2024} report 0.646 accuracy
for a Random Forest operating without deep features and 0.940 when the same
classifier uses a concatenated feature vector extracted by VGG16 and ResNet-50.
The paper describes the two networks as feature extractors but does not state
that they were frozen throughout. Zhou et al. \cite{Zhou2018} report the same
broad ordering on the benchmark used in this project, where CNN-derived
features outperform handcrafted descriptors for retrieval. Both results
motivate our decision to treat deep feature extraction, rather than feature
engineering, as the foundation of every approach we investigate.

\subsubsection{Benchmark Datasets}

Progress in this field has been driven by successive benchmarks --- UC Merced,
WHU-RS19, RSSCN7, AID, and NWPU-RESISC45 --- each larger or more finely
categorised than the last. Our data comes from \textbf{PatternNet}
\cite{Zhou2018}, a 38-class collection of 800 images per class at
$256 \times 256$ pixels, gathered over US cities via Google Earth imagery and
the Google Map API.

One design property of PatternNet directly shapes this project. The dataset was
constructed for \emph{image retrieval}, a task that rewards fine-grained
category distinctions, so it deliberately separates classes that a
coarser-grained benchmark would merge. Our partition inherits four such
categories --- \texttt{coastal\_mansion}, \texttt{dense\_residential},
\texttt{nursing\_home}, and \texttt{sparse\_residential} --- all of which are
residential or institutional building scenes. The difficulty we report in
Section~\ref{sec:results} is therefore intrinsic to the benchmark's design
rather than incidental to our partition.

\subsubsection{Convolutional Architectures}

The systematic review by Shoaib et al. \cite{Shoaib2025}, covering 124 studies
of deep learning for aerial imagery, identifies convolutional networks as the
dominant family for classification, valued for accuracy and computational
efficiency. Three developments in that family inform our choices.

\textbf{Residual learning.} ResNet \cite{He2016} introduced skip connections so
that each block learns a residual adjustment to its input, allowing gradients
to propagate through very deep stacks. ResNet-50 remains a standard baseline
with well-understood transfer behaviour, which is why we include it.

\textbf{Compound scaling.} EfficientNet \cite{Tan2019} observes that network
depth, width, and input resolution should be scaled together under a single
coefficient rather than independently, yielding markedly better accuracy per
parameter. Shoaib et al. \cite{Shoaib2025} single out this efficiency as
important for high-resolution aerial data, where computational cost scales
quickly with image size.

\textbf{Efficiency-oriented design.} MobileNetV2 \cite{Sandler2018} factorises
standard convolutions into depthwise and pointwise operations and adds inverted
residual blocks with linear bottlenecks, reducing parameter count by an order of
magnitude at modest accuracy cost. It represents the deployment-constrained end
of the design space, and the development of such lightweight models is
identified as a priority direction in \cite{Shoaib2025}.

\subsubsection{Transfer Learning under Limited Supervision}

With 700 training images per class, training a large network from random
initialisation risks overfitting. The standard remedy is transfer learning:
reusing representations learned on a large source corpus such as ImageNet.
Shoaib et al. \cite{Shoaib2025} state the case directly --- pretrained models
``provide robust feature representations that generalize well to aerial
imagery,'' and this ``is especially important for scenarios with limited
labeled data.''

The practical question is how much of the network to adapt. Kwenda et al.
\cite{Kwenda2024} take the conservative extreme, freezing VGG16 and ResNet-50
entirely and training only a downstream classifier, and still obtain strong
results. We adopt the same strategy for our three pretrained models: the
backbone is frozen and only a small classification head is fitted. This
suppresses overfitting on a small dataset and, equally important for our
purpose, holds the amount of adaptation constant across the transfer-learning
approaches so that the comparison reflects architecture rather than fine-tuning
effort.

\subsubsection{Attention and Vision Transformers}

Vision Transformers \cite{Dosovitskiy2021} discard convolution entirely,
partitioning an image into fixed patches and processing the resulting sequence
with self-attention. Every patch can attend to every other from the first
layer, capturing global spatial layout that a convolutional stack only reaches
after many layers --- a property well matched to aerial scenes, where the
discriminating cue is the arrangement of elements across the whole image.

This capability carries a known cost. Shoaib et al. \cite{Shoaib2025} caution
that transformers ``typically require large amounts of training data and
computational resources, which can be a limitation in domains like aerial image
analysis with limited annotated datasets.'' Whether that limitation binds at our
dataset scale is one of the questions this study answers empirically
(Section~\ref{sec:comparative}).

\subsubsection{Positioning of This Work}

The literature establishes that deep features outperform handcrafted ones, that
transfer learning is the standard response to limited data, and that
architectures differ in their accuracy-to-cost trade-offs. What it does not
readily provide is a \emph{controlled} comparison: published results differ in
input resolution, augmentation, optimiser, training schedule, and evaluation
protocol, so architectural claims are difficult to isolate. This project
addresses that gap on one dataset by fixing every such variable across five
architectures and varying only the model, as detailed in
Section~\ref{sec:splits} and Section~\ref{sec:augmentation}.

Perfect balance has two consequences for the rest of this report. First, plain

\subsection{Image Properties}

Sampling 100 images per class (400 in total) shows the collection to be
perfectly uniform: every image is $256 \times 256$ pixels with zero variance,
an aspect ratio of exactly $1.0$, and all 400 sampled images are in RGB mode.
No greyscale, CMYK, or alpha-channel images are present, and no corrupt files
were encountered.

This uniformity motivated a concrete team decision. The pipeline was
originally configured at the conventional ImageNet resolution of
$224 \times 224$, but because the source images are natively $256 \times 256$,
that setting discarded roughly 23\% of the available pixels before training
began. The shared external input was therefore standardised at
\texttt{IMAGE\_SIZE = 256}. The four CNNs operate on the data at that native
resolution; ViT accepts the same $256 \times 256$ tensor and then resizes it
internally to $224 \times 224$ to match its fixed position-embedding grid. The
trade-off is revisited in Section~\ref{sec:comparative}.

exactly the density-based distinctions rather than colour-based ones.

\subsection{Visual Confusability}

Inspecting sample grids per class confirms that this is a genuinely
fine-grained problem rather than a coarse one. All four categories are
suburban aerial scenes photographed at similar altitude, sharing the same
vocabulary of roofs, roads, and vegetation; they differ only in the
\emph{arrangement} and \emph{density} of those elements. Two pairs are
particularly difficult:

\begin{itemize}
  \item \texttt{dense\_residential} versus \texttt{sparse\_residential} --- an
    identical scene type separated only by a continuous, unlabelled density
    threshold, with no discrete visual boundary between them.
  \item \texttt{nursing\_home} versus \texttt{dense\_residential} --- both show
    clustered multi-unit buildings; the distinction rests on building
    footprint and layout regularity rather than on scene content.
\end{itemize}

These predictions were recorded before training and are directly confirmed by
the confusion matrices in Section~\ref{sec:results}.

\subsection{Data Quality: Duplicate Images}

One integrity problem was found. Two training files are byte-identical to each
other yet assigned to conflicting classes:

\begin{center}
\texttt{coastal\_mansion/coastalmansion029.jpg} \quad and \quad
\texttt{sparse\_residential/sparseresidential021.jpg}
\end{center}

The same image therefore carries two mutually exclusive labels. Left in place
it supplies contradictory gradients and, worse, could place identical pixels on
both sides of the train/tuning split --- a small but genuine leakage path.
Both files are excluded logically by the shared loader through
\texttt{EXCLUDED\_TRAIN\_FILES} in \texttt{shared/config.py}; the source data on
disk is never modified, so the exclusion is reproducible and auditable by every
team member. The usable training pool is consequently 2{,}798 images. Notably,
the affected pair belongs to the two classes that colour statistics already
identified as most similar.

\subsection{Implications for Modelling}

Four conclusions carried forward into the design:

\begin{enumerate}
  \item \textbf{Accuracy is a fair headline metric} (balanced classes), but
    macro-$F_1$ is reported alongside it to expose per-class collapse.
  \item \textbf{All models accept $256 \times 256$ inputs.} The four CNNs retain
    the native resolution; ViT alone performs a documented internal resize to
    $224 \times 224$.
  \item \textbf{Texture and structure, not colour, carry the signal}, so the
    augmentation policy must preserve fine-grained texture --- photometric
    jitter is kept deliberately mild for this reason
    (Section~\ref{sec:augmentation}).
  \item \textbf{Aerial scenes have no canonical orientation.} Unlike natural
    photographs, a top-down scene is equally valid flipped or rotated, so full
    horizontal and vertical flips and arbitrary rotations are
    \emph{label-preserving} here. This observation directly justifies the
    shared augmentation policy.
\end{enumerate}

\section{Data Preparation and Pre-Processing}
\subsection{Data Splits and Leakage Control}
\label{sec:splits}

A recurring flaw in student-scale deep learning experiments is that the same
data guides both model selection and final reporting, which inflates the
headline number without anyone intending to cheat. We designed the pipeline to
reduce that risk through a three-way split implemented once in
\texttt{shared/data.py} and shared by all five models.

\paragraph{Three-way split.}
The provided \texttt{val 23} directory is treated as a \emph{sealed test set}.
All development data is therefore carved out of \texttt{set 23} alone: a
deterministic stratified split assigns 85\% of it to model fitting and 15\% to
an internal \emph{tuning} set (Table~\ref{tab:splits}).

\begin{table}[H]
\centering
\caption{Three-way data split. Only the training subset updates weights; the
tuning subset guides checkpoint selection; the held-out set is untouched until
final evaluation.}
\label{tab:splits}
\small
\begin{tabular}{llrl}
\toprule
Subset & Source & Images & Role \\
\midrule
Training & \texttt{set 23} & 2{,}378 & gradient updates \\
Tuning   & \texttt{set 23} & 420 & early stopping, checkpoint selection \\
Held-out & \texttt{val 23} & 400 & final evaluation only \\
\bottomrule
\end{tabular}
\end{table}

The split is \emph{stratified}: it is drawn independently within each class, so
the tuning subset contains exactly 105 images per class and the training
subset 594--595 per class. Class balance is thus preserved on both sides rather
than left to chance, which matters because per-class $F_1$ on a 420-image
subset is sensitive to even small imbalances.

\paragraph{Determinism.}
Split repeatability is supported by seeding the shuffle for class $k$ with
$\texttt{SEED} + k$ (\texttt{SEED} $=42$) rather than by a global random state.
Consequently the partition depends on the file listing rather than execution
order or earlier random draws. Given the same dataset snapshot and software
contract, team members should derive the same subsets. The exact counts are
recorded in each run's metadata via \texttt{get\_split\_counts()}, so any run
can be audited after the fact.

\paragraph{Why the held-out set must stay sealed.}
Both \texttt{ModelCheckpoint} and \texttt{EarlyStopping} select the epoch that
maximises \emph{tuning} accuracy. That makes tuning metrics optimistically
biased by construction: they measure the best of roughly 30 attempts, not the
expected performance on new data. The effect is not hypothetical --- for our
custom CNN the tuning macro-$F_1$ of 0.908 overstates the held-out 0.845 by
more than six points. Every number reported in
Section~\ref{sec:results} is therefore held-out, and the tuning metrics are
retained only as a training diagnostic.

Mechanically, the held-out loader is a separate function that reads
\texttt{val 23} and is invoked only behind an explicit
\texttt{--evaluate-held-out} flag, after training has finished. It is never
passed to \texttt{model.fit} and never influences a callback. Combined with the
duplicate-image exclusion described above, this design keeps exact duplicate
pixels out of both the training and held-out evaluation paths under the shared
entrypoint.

\paragraph{Deviation from the literature protocol.}
Our effective proportions are approximately 74/13/13 rather than the 70/15/15
used by the reference architecture we follow, because the test partition is
fixed at 400 images by the provided data rather than chosen by us. Since the
identical split is applied to all five models, the split choice is controlled
across approaches even though its sampling uncertainty still affects the
comparison.
\subsection{Input Resolution}

All models accept $256 \times 256$ RGB inputs, the \emph{native} resolution of
every source image. The four CNNs retain that spatial resolution. ViT is the
documented exception: its saved graph applies bilinear resizing from
$256 \times 256$ to $224 \times 224$ immediately before the backbone because
its position embeddings are fixed to a $14 \times 14$ patch grid. Standardising
the external interface at 256 therefore gives every approach the same input
contract, but does not imply that every architecture preserves every source
pixel internally.

The trade-off is that the ImageNet-pretrained backbones no longer operate at
the resolution they were trained on. We accepted this deliberately: the
alternative penalises the from-scratch model (which has no such prior) in order
to flatter the pretrained ones, and comparability requires that all five
approaches see identical inputs. Resizing uses bilinear interpolation with
antialiasing enabled, which matters when a model internally rescales.

\subsection{Augmentation}
\label{sec:augmentation}

With only 2{,}378 training images against models of 2.3M--85.8M parameters,
augmentation is not an optional refinement but the main defence against
overfitting. The policy is defined once in \texttt{shared/augment.py} and
embedded as the first stage of every model, so it is applied identically across
all five approaches and is automatically inactive at inference time.

\end{tabular}
\end{table}

\paragraph{Geometric transforms are label-preserving here.}
For natural photographs a vertical flip produces an implausible image, and
practitioners routinely restrict augmentation to horizontal flips and small
rotations for that reason. Top-down aerial imagery has no such constraint: a
residential block photographed from above is equally valid rotated by any
angle or mirrored in either axis, and the class label is unchanged. Full
flips and arbitrary rotations are therefore \emph{free} additional training
signal rather than label noise, and we exploit them aggressively. Rotation
uses \texttt{reflect} fill so that rotated corners contain plausible texture
instead of black wedges, which would otherwise be a spurious cue correlated
with augmentation rather than with class.

\paragraph{Photometric transforms are kept deliberately mild.}
Contrast and brightness are restricted to $\pm 10\%$ --- an order of magnitude
weaker than the geometric transforms. This asymmetry is a direct consequence
of the exploratory finding that the four classes are \emph{not} separable by
colour: with all twelve channel means confined to a narrow band, the
discriminative signal lies in fine-grained texture and spatial structure.
Aggressive photometric jitter would degrade precisely the cues the models
depend on. This was confirmed empirically --- an early configuration using a
$\pm 50\%$ factor drove images to near-black or near-white and destroyed the
texture detail entirely, so the factor was reduced.

\paragraph{Ordering and value range.}
The augmentation layers operate on raw $[0,255]$ pixels and return values in
the same range, so any model-specific normalisation (a \texttt{Rescaling}
layer for the custom CNN, or the backbone's own \texttt{preprocess\_input} for
the transfer models) is applied \emph{after} augmentation. Placing rescaling
first is a subtle but real bug: the brightness layer is configured for a
$[0,255]$ value range, and feeding it $[0,1]$ inputs saturates the image to
black. Because augmentation lives inside the model graph rather than in the
data pipeline, this ordering is fixed at construction time and reduces the risk
of an inference-time ordering mismatch.

\paragraph{Augmentation is training-only.}
The Keras preprocessing layers are inactive outside training, and the tuning
and held-out datasets are never passed through the augmentation pipeline. All
reported metrics therefore reflect performance on clean, untouched images.

\paragraph{Status as a controlled variable.}
The policy is fixed and shared rather than tuned per model. Individual
architectures might well prefer slightly different settings, but allowing each
member to tune augmentation independently would confound the comparison: a
difference in final accuracy could then reflect a better augmentation search
rather than a better architecture. Holding augmentation constant --- along with
the data, split, external input contract, and evaluation procedure --- reduces
these sources of confounding and supports the architecture-focused comparison
in Section~\ref{sec:results}.

\subsection{Custom CNN (from scratch)}
\label{sec:customcnn}
% 26.5M total params; 26,511,444 trainable. No-pretraining baseline.

The custom CNN is the only approach in this study that uses no pretrained
weights. It contains 26,512,212 parameters in total: 26,511,444 trainable
parameters and 768 non-trainable BatchNorm moving-mean and moving-variance
state parameters. Its role is therefore twofold: it is a competitive
architecture in its own right, and it is the experimental control that makes
the contribution of ImageNet pretraining measurable rather than assumed --- a
comparison the other four approaches cannot provide on their own.

\subsubsection{Source Architecture}

Rather than assemble an arbitrary stack of layers, we reproduce the
\emph{Pyramidal Net} architecture proposed by Abdelmonem et al.
\cite{Abdelmonem2026}, which was designed specifically for remote-sensing scene
classification and reports 94.28\% accuracy on a ten-class NWPU-RESISC45 subset
and 93\% on UC~Merced. NWPU-RESISC45 contains 700 images per class, but the
source experiment allocates them 70/15/15 to training, validation, and test, so
its nominal training allocation is 490 images per class rather than our
provided 700-image training pool. The shared $256 \times 256$ resolution makes
the architecture relevant, while the different data budget prevents a
like-for-like performance comparison.

The name describes the design principle: spatial dimensions contract while
feature abstraction increases, so the representation narrows toward the
classifier like a pyramid. Table~\ref{tab:customcnn-arch} gives the structure as
implemented.

\subsubsection{Discussion}

Our result does not reproduce the ordering reported in \cite{Abdelmonem2026},
where the custom architecture is presented as competitive with or superior to
pretrained networks. On our partition it is decisively outperformed by all four
transfer-learning approaches, including MobileNetV2, which reaches 0.9576
macro-$F_1$ with 2.26M parameters --- roughly one twelfth of the custom model's
capacity.

We attribute the discrepancy to the granularity of the classification task
rather than to any defect in the architecture. The ten NWPU-RESISC45 categories
used in the source study --- harbour, chaparral, tennis court, industrial area,
parking lot, forest, beach, overpass, airplane, and baseball diamond --- are
semantically and visually disjoint, and are separable on coarse cues such as
dominant colour, the presence of water, or large geometric structures. Features
sufficient for those distinctions are learnable from 700 images per class. Our
four categories are all residential or institutional building scenes
distinguished by building density and spatial arrangement, and the
discriminative features are correspondingly subtler. ImageNet pretraining
supplies exactly the mid-level texture and structure detectors that such a task
demands and that 2,378 images are insufficient to induce from scratch.

It is also worth noting that the source paper's own comparison is more equivocal
than its abstract suggests: on NWPU-RESISC45 (its Table~7) VGG16 attains 0.949
and Xception 0.948 test accuracy against the proposed model's 0.9428, so the
architecture's advantage there rests on its efficiency and its markedly stronger
performance on the smaller UC~Merced dataset rather than on raw accuracy. Read
in that light, our finding is less a contradiction of \cite{Abdelmonem2026} than
a delineation of where its conclusions hold: a well-designed from-scratch CNN is
competitive on coarse-grained scene classification, but pretraining remains
decisive when categories are fine-grained and data is limited. Establishing that
boundary is precisely the contribution this baseline makes to our comparison,
and it is developed further in Section~\ref{sec:comparative}.
\subsection{ResNet-50 (transfer learning)}
% 23.6M total / 8.2K trainable — frozen ImageNet backbone + new head.
ResNet's key idea is the residual (skip) connection: each block learns an
adjustment to its input rather than a full transformation, which lets
gradients flow through many layers and made genuinely deep networks trainable
for the first time \cite{He2016}. ResNet-50, pretrained on ImageNet, is one of
the most widely used backbones in computer vision, with transfer behaviour
that is well understood making it one of the natural strong defaults among our
five approaches.

We use the backbone as a frozen feature extractor and train only a small new
classification head. The whole pipeline is packaged inside a single Keras
model (Table~\ref{tab:resnet50-config}): the saved checkpoint accepts raw
$[0, 255]$ RGB images and handles augmentation and preprocessing itself.

\subsection{EfficientNet-B0 (transfer learning)}
\label{sec:efficientnet}

EfficientNet was designed around a different question from ResNet: once a
competent convolutional network exists, how should additional computation be
distributed between depth, width, and input resolution? Tan and Le
\cite{Tan2019} show that scaling only one dimension produces an unbalanced
network and propose a compound coefficient that increases all three together.
EfficientNet-B0 is the neural-architecture-search baseline from which the larger
B1--B7 family is scaled. Its main operator is the mobile inverted bottleneck
(MBConv), inherited from MobileNetV2, augmented with squeeze-and-excitation
channel attention.

That design makes B0 a useful contrast to both ResNet-50 and MobileNetV2 in this
study. Against ResNet-50 it asks whether a much smaller, explicitly
efficiency-designed backbone can preserve fine-grained accuracy. Against
MobileNetV2 it asks whether squeeze-and-excitation and EfficientNet's searched
stage allocation buy accuracy beyond the common MBConv foundation.

\subsubsection{Architecture and Adaptation}

The Keras ImageNet checkpoint is used without its original 1,000-class head.
Global average pooling produces a 1,280-dimensional representation, followed by
the same dropout-plus-softmax head used for MobileNetV2. The complete
configuration is shown in Table~\ref{tab:efficientnet-config}.

Only 5,124 parameters --- 0.13\% of the network --- are updated. This is a

parameters reliably, while the ImageNet filters already encode edges, textures,
repeated structures, and spatial compositions relevant to aerial scenes.
Freezing also keeps the evaluation aligned with the other pretrained CNNs:
their representation quality is compared under a common four-class head rather
than confounded by different fine-tuning depths.

Our implementation makes three project-specific modifications. First, it
accepts the shared native $256\times256$ input rather than the paper's
$224\times224$ baseline resolution; global pooling permits this without
changing the classifier dimensions. Second, the shared aerial augmentation is
embedded before EfficientNet's preprocessing so the saved checkpoint accepts
raw images in both training and deployment. Third, the original 1,000-class
classifier is replaced by a four-class head whose dropout and learning rate
were exposed through the shared experiment interface. The selected values were
chosen from the internal tuning split before the held-out evaluation.

\subsection{MobileNetV2 (transfer learning)}
\label{sec:mobilenet}

MobileNetV2 is the explicitly resource-constrained member of our comparison.
Its basic unit is an inverted residual with a linear bottleneck
\cite{Sandler2018}. A conventional residual block compresses a wide
representation and then expands it again; MobileNetV2 reverses that pattern.
Each block expands a narrow input with a $1\times1$ convolution, filters the
expanded channels independently with a depthwise $3\times3$ convolution, and
projects them linearly back to a narrow output. Skip connections join the thin
bottlenecks when shape and stride permit.

Two details are important. Depthwise separable convolution avoids paying for a
full spatial kernel across every input-output channel pair, while the linear
final projection avoids destroying information with ReLU in the
low-dimensional bottleneck. The source paper reports that a $3\times3$
depthwise-separable operation is roughly eight to nine times cheaper than a
standard convolution at comparable channel dimensions \cite{Sandler2018}.
This makes MobileNetV2 a principled efficiency baseline rather than simply a
smaller arbitrary CNN.

\subsection{Vision Transformer (ViT)}
% 85.8M total / 3.1K trainable; input resize fix; attention-based contrast
% to the convolutional models.
The Vision Transformer \cite{Dosovitskiy2021} applies a pure Transformer
architecture to images: the input is split into fixed $16\times16$ patches,
each patch is linearly embedded and given a learned position embedding, and
the resulting sequence is processed by a stack of self-attention layers. Unlike a CNN, whose
convolutions can only relate nearby pixels layer by layer, self-attention
lets every patch attend to every other patch from the first layer onward,
capturing global layout cues directly. This makes ViT a structurally
different approach from our four convolutional models, which is exactly the
contrast our comparison needs: aerial scene categories such as dense versus
sparse residential are distinguished less by any single local texture than
by the overall spatial arrangement of buildings, roads, and vegetation.
Pretrained ViTs have already been shown to transfer effectively to
remote-sensing scene classification at exactly this kind of scale
\cite{Bazi2021}.

We use the ViT-B/16 backbone pretrained on ImageNet as a frozen feature
extractor and train only a small classification head on the CLS token
embedding. As with the other approaches, the whole pipeline is packaged
inside a single Keras model (Table~\ref{tab:vit-config}): the saved
checkpoint accepts raw $[0,255]$ RGB images and applies augmentation and
preprocessing itself.

\begin{table}[H]
\centering
\caption{ViT-B/16 model configuration.}
\label{tab:vit-config}
\small
\begin{tabular}{ll}
\toprule
Stage & Details \\
\midrule
Input & $256\times256\times3$, raw $[0,255]$ RGB \\
Augmentation & shared team policy, active during training only \\
Resize & $256\times256 \rightarrow 224\times224$ (bilinear), see below \\
Preprocessing & scale to $[-1,1]$ (ViT convention, not ImageNet channel stats) \\
Backbone & ViT-B/16, ImageNet weights, frozen; 12 layers, 768 hidden dim, 12 heads \\
Head & CLS token $\rightarrow$ dropout 0.3 $\rightarrow$ dense softmax (4 units) \\
Parameters & 85{,}801{,}732 total; 3{,}076 trainable \\
Optimisation & Adam, learning rate $10^{-3}$, categorical cross-entropy \\
\bottomrule
\end{tabular}
\end{table}

The model resizes its input from the shared $256\times256$ to $224\times224$ immediately before the backbone. 
This is not optional: ViT's learned position embeddings form
a fixed table with one entry per patch position ($14\times14$ patches
$+$ CLS $=$ 197 tokens for a $224\times224$ input), so a $256\times256$
input would produce 257 tokens with no pretrained embedding to match. CNNs
tolerate off-resolution input silently because convolution weights are
shared across positions; ViT makes the mismatch explicit. Notably, the CNN
backbones used by the other approaches were also pretrained at
$224\times224$, so our ViT is arguably the only model evaluated at its
native pretraining resolution. The resize is placed after the shared
augmentation, so regularisation is applied identically to all five models.
Second, the backbone is frozen: ViTs lack the inductive biases of
convolutions and are known to need large datasets or heavy augmentation
when trained or fine-tuned directly \cite{Dosovitskiy2021,Touvron2021}, so
with only 2{,}798 usable training images we fit just the 3{,}076-parameter head
--- by far the smallest trainable footprint of our five approaches, which
limits its capacity to overfit the tuning split. Third, preprocessing scales
pixels to $[-1,1]$ rather than applying ImageNet channel normalisation,
matching how this checkpoint was pretrained.

\paragraph{Choice of variant.}
ViT-B/16 is the canonical member of the family --- the configuration the
original paper itself headline-reports \cite{Dosovitskiy2021} --- and each
alternative variant was excluded on grounds specific to this task. Patch-32
variants retain a quarter of the tokens ($7\times7$ vs.\ $14\times14$ at
224 pixels), discarding exactly the spatial resolution the fine-grained
density classes depend on. The 384-pixel presets would \emph{upsample} our
native 256-pixel imagery for no information gain at three times the token
count. Larger backbones (ViT-L, 307M parameters) could raise accuracy only
marginally under a frozen linear probe \cite{Kornblith2019} while worsening
the cost--accuracy trade-off that Section~\ref{sec:comparative} shows
already disfavours ViT's footprint. Partial fine-tuning of the upper
transformer blocks is the one variant with genuine potential to close the
accuracy gap to the best CNNs, but it would break the frozen-backbone
protocol that keeps the five-way comparison clean; we defer it to
Section~\ref{sec:future}.

\paragraph{Pretraining-source ablation.}
\label{sec:vit-ablation}
The choice of pretrained weights was validated experimentally rather than
assumed. The selected checkpoint was pretrained on ImageNet-21k and then
finetuned on ImageNet-1k, following the AugReg release lineage
\cite{Steiner2022}; we compared it against the raw ImageNet-21k
weights (never finetuned to the 1k label space) under an otherwise identical
protocol --- same seed, split, augmentation, and training flags. Our
hypothesis was that the more generic 21k features would transfer better to
aerial imagery, which is a clear domain shift from natural photos. To keep
the held-out set untouched by model selection, the comparison used the
internal tuning split only (Table~\ref{tab:vit-ablation}).

The hypothesis was cleanly falsified: the 1k-finetuned checkpoint scored
1.4 points higher macro-$F_1$ and converged three times faster (best epoch

ended). The explanation lies in how the features are used. Supervised
finetuning on the 1k label space shapes the CLS embedding to be linearly
separable --- precisely what a frozen-backbone setup with a softmax head
requires, consistent with the strong dependence of penultimate-feature
transfer on the pretraining objective observed by Kornblith et
al.~\cite{Kornblith2019}. The raw 21k features are not poorer, but more entangled: a
3{,}076-parameter head can only draw four hyperplanes through the
768-dimensional embedding space and cannot re-mix features, so it benefits
from geometry that finetuning has already organised. The slow crawl of the
21k run is the visible signature of that harder optimisation problem. With
full fine-tuning the outcome could well reverse; in the frozen regime, the
linear-separability effect dominated the domain-shift effect. The 1k
variant was therefore retained, and only it was evaluated on the held-out
set.

\section{Model Training and Tuning}
\label{sec:training}

\subsection{Shared Training Protocol}

Every final run in this report was produced by a single training entrypoint,
\texttt{train.py}, rather than by five separate scripts. Each model is a module
under \texttt{models/} that exposes one function,
\texttt{build\_model(num\_classes, augmentation)}; the entrypoint injects the
shared augmentation pipeline, builds the shared data splits, trains, selects a
checkpoint, and writes results in a fixed schema. Keeping split construction,
augmentation, and evaluation outside the per-model modules reduces accidental
protocol drift and makes deviations visible in shared code and metadata.
Table~\ref{tab:protocol} lists the variables held constant across all five
final runs.

Checkpoint selection and early stopping both monitor accuracy on the internal
tuning split; the held-out set is reachable only through a separate loader
behind an explicit \texttt{--evaluate-held-out} flag, as described in
Section~\ref{sec:splits}. Repeatability is supported at two levels: the
shared \texttt{set\_seed()} seeds every random number generator and enables
TensorFlow's deterministic kernels, and every run writes a metadata record
(\texttt{results/<run>\_run.json}) capturing the git commit, seed, split
counts including the excluded duplicate files, total and trainable parameter
counts, best epoch, and TensorFlow version. Any number in this report can
therefore be traced back to the exact code and data state that produced it.

Two per-model extension points keep the protocol from being a straitjacket.
A model may expose \texttt{configure(dropout, learning\_rate)} to accept
head hyper-parameters from the command line, and \texttt{get\_callbacks()} to
add callbacks justified by that member's own research --- the custom CNN uses
this hook for the \texttt{ReduceLROnPlateau} schedule specified by its source
paper (Section~\ref{sec:customcnn}). Neither hook can alter the data, the
augmentation, or the evaluation.

\subsection{Hyper-parameter Tuning}

All hyper-parameter selection used the internal tuning split only; the
held-out set was never consulted. The four transfer models share the same
two-parameter head (dropout rate and learning rate), and all four final runs
used dropout $0.3$ and learning rate $10^{-3}$. These values were not simply
assumed:

\begin{itemize}
  \item \textbf{EfficientNet-B0} ran a one-factor-at-a-time experiment suite
    under a shortened budget (15 epochs, patience 3): the baseline
    (dropout 0.3, LR $10^{-3}$) against a lower learning rate
    ($3 \times 10^{-4}$) and against stronger dropout (0.4). Runs were ranked
    by tuning macro-$F_1$, the baseline won, and only the winning
    configuration was retrained under the full 32-epoch protocol.
  \item \textbf{ViT} validated its choice of pretrained weights with the
    pretraining-source ablation of Section~\ref{sec:vit-ablation}, again
    selected on the tuning split alone.
  \item \textbf{The custom CNN} takes its optimiser settings from its source
    paper rather than from a search, since faithful reproduction was the point
    of that baseline; the one free coefficient (L2 strength) is documented in
    Section~\ref{sec:customcnn}.
\end{itemize}

This is deliberately light tuning. With frozen backbones the head has at most
8,196 trainable parameters, so the search space that matters is small, and we
preferred spending the budget on a clean architecture comparison over
per-model searches that would have confounded it.

\subsection{Convergence}

Because the epoch budget, batch size, seed, and data are identical across
runs, convergence is compared directly in epochs --- a measure independent of
each member's local machine --- using the best-epoch column of
Table~\ref{tab:leaderboard} and the per-model curves in Section~4
(Figures~\ref{fig:customcnn-curves}, \ref{fig:resnet50-curves},
and~\ref{fig:vit-curves}).

The five runs span the full range of the budget. ViT locked on by epoch 10
--- its frozen CLS embedding is already organised for linear classification,
so the 3,076-parameter head has little left to learn --- and was the only run
to trigger early stopping (halting at epoch 30, best epoch 10 plus
patience 20). The custom CNN and ResNet-50 peaked mid-schedule (epochs 24
and 25). MobileNetV2 and EfficientNet-B0 were still improving late: at best
epochs 30 and 32 respectively, EfficientNet-B0's checkpoint falls on the
final epoch of its budget, which suggests a longer schedule could squeeze
out slightly more and is noted as a limitation in
Section~\ref{sec:discussion}. That the fastest- and slowest-converging
models are both frozen-backbone transfer models with near-identical heads
shows convergence speed here is a property of how linearly separable the
pretrained embedding already is, not of trainable capacity.

\section{Inference and Performance Evaluation}
\subsection{Evaluation Protocol}

All reported metrics are produced by a single shared function,
\texttt{evaluate()} in \texttt{shared/evaluate.py}, so every model is scored
by identical code. For a given model and dataset it computes accuracy,
per-class precision, recall, and $F_1$ with supports, their macro averages,
and the confusion matrix (via scikit-learn), and writes them to a
fixed-schema JSON file plus a rendered confusion-matrix PNG under
\texttt{results/}. The fixed schema is what makes the cross-model tables in
this section possible without any manual transcription --- every number below
is read directly from those artifacts.

The held-out evaluation itself follows the protocol of
Section~\ref{sec:splits}: after training completes, the best checkpoint
(selected on tuning accuracy) is restored and applied exactly once to the 400
sealed images of \texttt{val 23} (100 per class), loaded through the separate
held-out loader behind the \texttt{--evaluate-held-out} flag. Augmentation
layers are inactive at inference, so models are scored on clean images.
Because the held-out set is exactly balanced, macro recall coincides with
accuracy --- a property visible in Table~\ref{tab:leaderboard} that doubles
as a sanity check on the pipeline.

\paragraph{Error counts and statistical resolution.}
In absolute terms the models misclassify 9 (EfficientNet-B0), 10 (ResNet-50),

interval on 400 trials spans roughly $\pm 1.5$ accuracy points at the top of
the table (and $\pm 3.5$ points at the custom CNN's level). The ordering
among the four transfer models is therefore suggestive rather than settled
--- all four intervals overlap --- whereas the gap between any transfer model
and the from-scratch baseline is far outside any interval and is the one
statistically unambiguous conclusion this test set can support. This caveat
is carried into the recommendation in Section~\ref{sec:discussion}.

Confusion matrices for each model, and the per-model diagnosis of where the
errors sit, are given alongside the corresponding architecture in
Section~4; the cross-model view of those errors is taken up in
Section~\ref{sec:comparative}.

\section{Strengths, Weaknesses, and Comparative Insights}
\label{sec:comparative}

\subsection{Per-Approach Assessment}

\paragraph{Custom CNN (Pyramidal Net).}
Its strength is exactly its role: as the only model with no external weights,
it isolates what our 2,378 images alone can teach, and on classes with a
global, scene-level cue it is genuinely competitive ($F_1 = 0.990$ on
\texttt{coastal\_mansion}, with perfect precision). Its weaknesses follow
from its capacity being in the wrong place: 97\% of its 26.5M parameters sit
in a single dense layer fitted to a few thousand images, producing the
largest train--validation gap of the study, the worst held-out accuracy
(0.8450), a collapse on the density boundary (dense-residential recall
0.64), and a 6.3-point gap between tuning and held-out macro-$F_1$ --- the
least trustworthy validation signal of the five. It is also the only model
whose early training was unstable (Figure~\ref{fig:customcnn-curves}).

\paragraph{ResNet-50.}
The strong default lived up to its reputation: 0.9750 accuracy, no class
below $F_1 = 0.964$, smooth convergence, and a small observed
tuning-to-held-out gap ($-0.006$ macro-$F_1$). Its weakness is
cost-effectiveness rather than
quality: it needs 23.6M parameters to reach an accuracy that EfficientNet-B0
statistically matches with a sixth of them. As a deployment artifact it is
the largest CNN checkpoint in the study for no measurable accuracy benefit.

\paragraph{EfficientNet-B0.}
The best result of the study --- 0.9775 accuracy and macro-$F_1$ with only
4.1M total parameters and 5,124 trainable --- and the only model to hold
every class at $F_1 \geq 0.970$. Compound scaling's accuracy-per-parameter
promise \cite{Tan2019} is borne out at the smallest scale of the family. Its
hyper-parameters were also the most systematically chosen, via a
one-factor-at-a-time suite (Section~\ref{sec:training}). Two caveats: its
best epoch was the last epoch of the budget, so it is plausibly slightly
undertrained, and its margin over ResNet-50 is one image --- a tie within
noise, not a demonstrated superiority.

\paragraph{MobileNetV2.}
The efficiency extreme: 2.3M parameters --- 2.6\% of ViT's footprint ---
still delivers 0.9575 accuracy, making it the best accuracy-per-parameter in
the study and the natural choice if the classifier had to run on an edge
device such as a drone or embedded mapping unit \cite{Sandler2018}. Its
weakness is that it is the least accurate of the transfer models, and its
error signature differs from the others: its largest single confusion is
\texttt{dense\_residential} $\rightarrow$ \texttt{nursing\_home} (7 images)
rather than the dense$\rightarrow$sparse confusion that dominates elsewhere,
suggesting its aggressively factorised features blur the
building-footprint cues that separate institutional from residential blocks.

\paragraph{Vision Transformer (ViT-B/16).}
The structural outlier earns its place in the comparison: it converged
fastest (best epoch 10), and its held-out macro-$F_1$ was 0.010 above its
tuning value, so no positive tuning-to-held-out optimism was observed in this
run. It also showed that frozen global self-attention can transfer to this
aerial-imagery task. But at this dataset scale its costs are not repaid: 85.8M
parameters --- by far the heaviest training and inference footprint of the
study --- for an accuracy 1.0 point \emph{below} ResNet-50. In Pareto terms
ResNet-50 dominates it on both size and accuracy. The literature's caution that transformers want more data
\cite{Shoaib2025} is thus refined by our result: a frozen ViT is perfectly
\emph{usable} at 2,378 images, but nothing about the task rewarded its extra
capacity.

Plotting accuracy against parameter count, only two models sit on the Pareto

statistically indistinguishable accuracy --- and ViT is dominated by

parameters than three of the four transfer models and 11--13 points less
accuracy. For any deployment scenario in this study's range, the practical
menu is therefore EfficientNet-B0 by default and MobileNetV2 when the size
budget is severe.

\subsection{Data Efficiency: What Pretraining Buys}

The comparison quantifies transfer learning's value on this task with unusual
directness, because everything except pretraining is controlled. Fitting
3,076--8,196 head parameters on frozen ImageNet features beats fitting 26.5M
parameters from scratch by 11.25--13.25 accuracy points, at a fraction of the
training cost. Moreover, the deficit is concentrated precisely where the task
is fine-grained: the from-scratch model matches the transfer models on
\texttt{coastal\_mansion} (a coarse, colour-and-shoreline cue) and loses
massively on the density classes (Table~\ref{tab:perclass}). This is the
boundary sketched in Section~\ref{sec:customcnn}: from-scratch CNNs suffice
for coarse scene vocabulary, while fine-grained spatial-arrangement
distinctions demand either far more data or borrowed mid-level features. Our
result thus lands on the same side as Kwenda et al.\ \cite{Kwenda2024} and
the review consensus \cite{Shoaib2025}, but with the confound of differing
pipelines removed.

\subsection{Capacity and the Trustworthiness of Validation Metrics}

The $\Delta F_1$ column of Table~\ref{tab:comparative} completes the analysis
threaded through Section~4. Checkpoint selection maximises tuning accuracy, so
a negative gap is consistent with selection optimism. The custom CNN shows a
$-6.3$-point gap and ResNet-50 a $-0.6$-point gap; for models with
3,076--5,124 trainable parameters the sign reverses and held-out performance
slightly exceeds tuning. These observations are consistent with reduced
selection overfit when only a small head is trained, but a single run and two
small evaluation sets do not identify the true bias or distinguish it from
sampling variability. The practical implication is therefore cautious:
freezing the backbone can make validation-based selection more stable, while
validation scores from high-capacity models warrant greater scrutiny.

\subsection{Error Overlap and Diversity}

Do the five models fail on the same images? At the class level, largely yes:
every confusion matrix concentrates its mass on the
dense/sparse-residential boundary, and no model ever confuses
\texttt{coastal\_mansion} with \texttt{nursing\_home} in either direction ---
the two classes with distinctive global structure. The custom CNN's errors
look like a magnified superset of the transfer models' errors rather than a
different failure mode.

Within the transfer models, however, the \emph{direction} of error differs
instructively. ResNet-50 and EfficientNet-B0 spread their few errors thinly
with a slight dense$\rightarrow$sparse lean; ViT's largest single cell is the
reverse, sparse$\rightarrow$dense (4 images); MobileNetV2's is
dense$\rightarrow$nursing-home (7 images). The top models are therefore not
making identical mistakes, which has a concrete consequence: a majority vote
or probability-averaging ensemble of ResNet-50, EfficientNet-B0, and ViT
would plausibly recover several of the 9--14 residual errors each makes
alone. We flag this as future work (Section~\ref{sec:future}) rather than
reporting it, because building an ensemble after seeing held-out results
would itself constitute test-set leakage under our protocol.

\section{Deployment via Containerisation}
\label{sec:deployment}
% NOTE: the dockerfile, .dockerignore allow-list, and frontend/web.py MODEL_PATH
% must all point at efficientnet_b0_best.keras before the final build.

A model that exists only as a checkpoint in a researcher's working directory is
not usable by anyone else. The final stage of this project therefore packages
the best-performing classifier as a self-contained container image that accepts
an aerial image through a web interface and returns a predicted category with
per-class confidence scores.

\subsection{Deployed Model}

The deployed classifier is \textbf{EfficientNet-B0}. Every architecture and
checkpoint was fixed using the internal tuning split before the five frozen
models were evaluated once on held-out data. EfficientNet-B0 then produced the
highest held-out macro-$F_1$ (0.9775, Section~\ref{sec:results}) and was packaged
as the assignment's best-performing demonstrator. This post-evaluation
packaging decision did not feed back into training, hyper-parameter selection,
or another held-out run. It is also a practical choice independently of the
one-image lead over ResNet-50: at 4.05M parameters its checkpoint is roughly an
order of magnitude smaller than the custom CNN's 304\,MB, which materially
affects image size, registry push time, and container start-up.

\subsection{Container Architecture}

The image is built from \texttt{python:3.12-slim} and contains four layers of
interest, ordered so that the expensive dependency installation is cached and
only the cheap application layers rebuild when code changes
(Table~\ref{tab:container}).

\begin{table}[H]
\centering
\caption{Container image composition.}
\label{tab:container}
\small
\begin{tabular}{lll}
\toprule
Layer & Contents & Purpose \\
\midrule
Base & \texttt{python:3.12-slim} & minimal Python runtime \\
Dependencies & \texttt{frontend/requirements.txt} & Streamlit, TensorFlow-CPU, Pillow, NumPy \\
Shared code & \texttt{shared/} & class names and input size from \texttt{config.py} \\
Application & \texttt{frontend/web.py} & Streamlit inference interface \\

\bottomrule
\end{tabular}
\end{table}

The container exposes port 8501 and declares a \texttt{HEALTHCHECK} that polls
Streamlit's \texttt{/\_stcore/health} endpoint, so an orchestrator can
distinguish a started container from a genuinely ready one. The entrypoint runs
Streamlit bound to \texttt{0.0.0.0} so the service is reachable from outside the
container.

\subsection{Inference Pipeline}

At request time the application performs four steps: it loads the uploaded file
and converts it to RGB, resizes it to the \texttt{IMAGE\_SIZE} imported from
\texttt{shared/config.py}, runs a single forward pass, and renders the result as
a predicted label with its confidence percentage plus a bar chart of the full
softmax distribution over all four classes. Presenting the complete distribution
rather than only the argmax is deliberate: on a fine-grained problem where
\texttt{dense\_residential} and \texttt{sparse\_residential} are genuinely
confusable, a user benefits from seeing that a prediction was made at 0.55
against 0.40 rather than at 0.99.

The model is loaded once and cached with Streamlit's
\texttt{@st.cache\_resource} decorator, so the checkpoint is deserialised on
first request rather than on every upload. Loading is wrapped in exception
handling: if the checkpoint cannot be read --- most plausibly a Keras version
mismatch --- the interface starts in a clearly labelled preview mode and
displays the underlying error rather than failing silently or crashing.

\subsection{Design Decisions}

Three choices are worth justifying.

\textbf{Preprocessing travels with the model.} Augmentation and any
normalisation are layers \emph{inside} the saved Keras graph rather than steps
in a separate inference script. Reusing graph-level normalisation at inference
reduces the risk of incorrectly scaled inputs and training--serving skew; the
container therefore needs no separate normalisation implementation.

\textbf{The container imports the same configuration module as training.}
Class names and input resolution are read from \texttt{shared/config.py}, the
same configuration module used to produce the checkpoint. This shared source,
together with the deployment contract test, makes label-order drift detectable
and avoids a second hard-coded class list in the application.

\textbf{CPU-only TensorFlow.} The image pins \texttt{tensorflow-cpu} rather
than the full distribution. Inference on a single image does not benefit
meaningfully from a GPU, and the CPU build avoids bundling CUDA libraries that
would inflate the image substantially and require GPU-enabled hosts.

\subsection{Build and Deployment}

The image is built and published with:

\begin{verbatim}
docker build -t <username>/<repository>:<version> .
docker push <username>/<repository>:<version>
docker run --name <container> -p 8501:8501 <username>/<repository>:<version>
\end{verbatim}

The interface is then available at \texttt{http://localhost:8501}. Because
trained checkpoints exceed the file-size limits of our version-control host,
\texttt{*.keras} artifacts are excluded from the repository and distributed
through the container image instead; a \texttt{.dockerignore} allow-list admits
only the single checkpoint being served, keeping the other models' weights out
of the build context.

\subsection{Verification and Limitations}

Deployment was verified by building the image, starting the container, receiving
HTTP 200 from its health endpoint, and submitting the held-out image shown in
Figure~\ref{fig:deployment-ui}. The running service loaded the selected
EfficientNet-B0 checkpoint and returned \texttt{coastal\_mansion} at 96.3\%
confidence. The repository also includes automated contract tests
(\texttt{tests/}) for the shared data and training pipelines plus the deployed
model path, checkpoint deserialisation, image preprocessing, output shape, and
probability normalisation. These tests establish that the data split is
deterministic and disjoint, that the duplicate-label conflict is excluded, and
that the model served by Docker follows the same raw-input and fixed-class
contracts used during evaluation.

Two limitations should be acknowledged. First, the interface itself is not
covered by automated tests --- verification is manual, through the running
container. Second, the service is a single-container demonstrator: it performs
no batching, authentication, request logging, or horizontal scaling, and would
require an orchestration layer and a proper inference server before production
use. These are deliberate scope boundaries rather than oversights, given that
the coursework requirement is a working containerised demonstrator.

\section{Results, Insights, and Discussion}
\label{sec:discussion}

\paragraph{What this benchmark says about fine-grained aerial classification.}
The headline finding is that four visually confusable residential categories
--- the deliberately fine-grained partition PatternNet was designed to
produce \cite{Zhou2018} --- are solvable to 96--98\% accuracy by frozen
ImageNet features with a head of a few thousand parameters. No fine-tuning,
no task-specific architecture, and no aggressive hyper-parameter search were
needed to reach that level. The genuinely scarce resource in this regime is
not model capacity but labelled data, and pretraining is how capacity is
converted into something 2,378 images can steer: the same experiment run
without pretraining (our custom CNN) lands 13 macro-$F_1$ points lower
despite having more parameters than three of the four transfer models.
Architecture choice \emph{among} pretrained backbones, by contrast, is worth
at most 2 points on this task --- second-order compared with the decision to
transfer at all.

\paragraph{Where the remaining errors live.}
Every model's residual errors concentrate on the dense-versus-sparse
residential boundary, exactly as the exploratory analysis predicted before
any training. We read this less as a model deficiency than as a property of
the label space: density is a continuous quantity that the benchmark
discretises into two names, so scenes near the threshold are inherently
ambiguous --- the dataset itself contains one image assigned to two classes
(Section~2.5), direct evidence that even the annotation process struggled at
this boundary. Accuracy meaningfully above 98\% on this partition would
likely require modelling that ambiguity (soft labels, ordinal density
regression) rather than a better classifier.

\paragraph{Final model recommendation.}
We recommend \textbf{EfficientNet-B0} as the final model. It tops the leaderboard
(0.9775 accuracy and macro-$F_1$), holds every class at $F_1 \geq 0.970$,
and does so with the second-smallest parameter count and the smallest
checkpoint among the top models --- there is no axis on which a rival beats
it by more than noise. We state the caveat plainly: its margin over
ResNet-50 is one image on a 400-image test set, so the honest claim is
``statistically tied for best accuracy while several times cheaper,'' which
is itself a sufficient reason to choose it. If the deployment budget were
tightened to embedded hardware, MobileNetV2 gives up 2 accuracy points for a
45\% smaller network and would be the rational trade.

\paragraph{Limitations.}
Four limitations bound our claims. (i) Every result is a single run at seed
42; without repetition across seeds we cannot attach variances. Fixed seeds,
deterministic operations, and recorded metadata improve repeatability within
the pinned environment, but exact cross-machine equivalence was not
experimentally established. (ii) The
400-image test set implies roughly $\pm 1.5$-point confidence intervals at
the top of the leaderboard, so the ordering among the four transfer models is
not statistically resolved --- only the transfer-versus-scratch gap is.
(iii) All four backbones were fully frozen. This was a deliberate controlled
variable, but it means we measured pretrained \emph{representations}, not the
ceiling of each architecture under fine-tuning; EfficientNet-B0's best epoch
landing on the final epoch of its budget likewise hints at headroom we did
not spend. (iv) The augmentation policy, input resolution, and other shared
settings were fixed for comparability rather than tuned per model, so each
individual model is likely slightly below its own optimum --- the price of a
fair comparison, paid knowingly.

\section{Reflection}

\subsection{Evaluation Discipline Is a Design Problem, Not a Willpower Problem}

The lecture-level statement ``do not tune on your test set'' sounds like an
instruction to be careful. The lasting lesson of this project is that
carefulness does not scale across five people and dozens of runs --- the
protection has to be built into the code. We designed the pipeline so that
the held-out loader is a separate function behind an explicit flag, never
passed to \texttt{model.fit} and never visible to a callback. This separation
makes accidental leakage less likely and easier to audit, although the explicit
evaluation flag means the protocol still depends on disciplined use.

The payoff was concrete. Our custom CNN's tuning macro-$F_1$ of 0.908
overstated its true held-out 0.845 by more than six points, with the entire
gap concentrated in one class. Had we reported tuning metrics --- a natural
mistake, since the model never received gradients from those images --- we
would have published the wrong number \emph{and} the wrong conclusion about
which class was solved. Watching that gap shrink to zero as trainable
capacity fell across the other four models turned an abstract warning about
validation optimism into something we measured ourselves. None of us will
again read a validation score without asking how much capacity the model had
to fit the validation set's idiosyncrasies.

\subsection{A Controlled Comparison Is a Team Contract}

We set out to compare architectures, and learnt that the comparison is only
as good as the discipline around it. Fixing the seed, split, input size,
batch size, epoch budget, augmentation policy, and evaluation code across
five members meant freezing \texttt{shared/} early and treating changes to it
as team-wide events, because any silent change would invalidate everyone's
prior runs. The fixed result schema was the quiet hero: because every run
wrote the same JSON structure, cross-model tables assembled themselves
without transcription, and each run's metadata (git commit, seed, split
counts, parameter counts, best epoch) made every number in this
report auditable months later.

We also learnt when to renegotiate the contract. The pipeline originally used
$224 \times 224$ inputs; the EDA showed this discarded 23\% of native pixels,
and changing it was cheap precisely because we caught it before anyone had
results to invalidate. The general lesson: agree the controlled variables
before training starts, change them only by consensus, and instrument
everything so that each reported number remains traceable to recorded
configuration and metadata.

\subsection{Transfer Learning in a Low-Data Regime}

Three findings reshaped our intuitions. First, the sheer size of the
pretraining effect: heads of 3,076--8,196 parameters on frozen ImageNet
features beat 26.5M parameters trained from scratch by 11--13 points,
and the deficit concentrated exactly on the fine-grained density distinctions
--- pretraining supplies the mid-level texture detectors that small data
cannot. Second, published orderings do not transfer across task granularity:
the source paper behind our custom CNN reports it competitive with pretrained
networks on semantically disjoint categories, and that conclusion simply did
not survive contact with four confusable residential classes. Reproducing a
paper faithfully and then explaining the divergence taught us more than
either step alone. Third, assumptions are cheap to test and often wrong: we
expected raw ImageNet-21k features to transfer better to aerial imagery than
1k-finetuned ones, ran the ablation, and were cleanly refuted --- in a
frozen-backbone regime, the linear separability that supervised finetuning
imposes matters more than feature generality.

\subsection{Engineering Lessons from the Debugging Trail}

The bugs we hit were more instructive than the code that worked first time.
The ViT input-size failure was the sharpest: CNN backbones silently accept
$256 \times 256$ inputs because convolution weights are position-agnostic,
but ViT's fixed position-embedding table made the same mismatch a hard error,
forcing us to understand \emph{why} the two families differ rather than just
resizing and moving on. The augmentation-ordering bug was subtler: placing
rescaling before the brightness layer --- which is configured for a
$[0,255]$ range --- silently saturated images to black, a reminder that
numerically valid pipelines can still be semantically wrong, and that
augmented batches should be visualised, not assumed. An early $\pm 50\%$
photometric jitter that destroyed the very texture cues our EDA said the task
depends on taught the same inspect-your-data lesson from the other side.

Environment work was its own education: getting TensorFlow's GPU path
working under WSL2 and pinning Python and TensorFlow versions across five
machines. Deterministic settings, identical split rules, and recorded metadata
reduced the risk of unnoticed differences between five development
environments, while hardware and dependency variations could still affect
exact numerical reproduction. The
automated contract tests earned their keep repeatedly, catching regressions
in the split logic before they could corrupt anyone's run. If we started
again, we would write those tests first, not midway.

\subsection{What We Would Do Differently}

Beyond starting with the tests, we would budget training time by
architecture rather than uniformly --- EfficientNet-B0's best epoch landing
on its final epoch shows a flat 32-epoch cap does not fit every model
equally. We would also schedule multiple seeds from the outset; single-run
results were the right trade under our compute constraints, but the
confidence-interval analysis of Section~\ref{sec:results} would have been
stronger as an empirical variance. Both are carried into
Section~\ref{sec:future}.

\section{Future Work}
\label{sec:future}

\paragraph{Partial fine-tuning with discriminative learning rates.}
The most direct extension is to unfreeze the top blocks of the winning
backbones with a learning rate one to two orders of magnitude below the
head's, keeping earlier layers frozen. Our frozen-backbone protocol measured
pretrained representations, not each architecture's ceiling, and two signs
point to headroom: EfficientNet-B0's best epoch fell on the last epoch of
its budget, and the residual errors are fine-grained texture judgements ---
exactly what adapting the top convolutional blocks to aerial imagery should
help. The selection discipline must carry over: any fine-tuning experiment
would be ranked on the internal tuning split, with the held-out set touched
once at the end.

\paragraph{Ensembling and test-time augmentation.}
Section~\ref{sec:comparative} showed the top models err in different
directions (ResNet-50 and EfficientNet-B0 lean dense$\rightarrow$sparse, ViT
the reverse, MobileNetV2 toward \texttt{nursing\_home}), which is precisely
the diversity an averaging ensemble exploits; with only 9--14 errors per
model, recovering even a handful would be a meaningful relative gain.
Test-time augmentation is a natural companion on aerial data: since flips
and rotations are label-preserving here, averaging predictions over the
dihedral group costs only inference time and no retraining. Both must be
designed \emph{before} a fresh evaluation --- assembling an ensemble to fix
errors already observed on the held-out set would be selection on the test
set.

\paragraph{Multiple seeds and statistical testing.}
Rerunning the five final configurations over several seeds would replace our
single-run leaderboard with means and variances, and paired tests (e.g.\
McNemar's on the 400 held-out predictions) could establish whether
EfficientNet-B0's one-image margin over ResNet-50 ever becomes a real
ordering. This is the cheapest way to firm up the study's weakest
statistical point.

\paragraph{Interpretability of the density decision.}
Grad-CAM on the convolutional models and attention-map visualisation on ViT
would test our standing interpretation directly: that
\texttt{coastal\_mansion} is recognised by shoreline, and that dense/sparse
errors occur on scenes near the density threshold. Confirming that the
models attend to buildings and spacing --- rather than to spurious cues such
as image brightness --- would also strengthen the case for deploying the
classifier on imagery from other regions.

\paragraph{Calibration and abstention.}
The inference interface reports softmax confidence, but we never measured whether 0.9
confidence means 90\% correctness. Measuring calibration error on held-out
predictions, applying temperature scaling if needed, and adding an
``uncertain --- refer to a human'' band for borderline density cases would
make the confidence output operationally meaningful, which matters for the
mapping and planning applications that motivated the task.

\paragraph{Hardened serving path.}
The Streamlit UI suits demonstration; a production path would add a FastAPI
REST endpoint alongside it (machine-to-machine JSON inference), container
build-and-health checks in CI, and a quantised or TensorFlow-Lite export ---
most naturally of MobileNetV2 --- for on-device inference, subject to
verifying metric parity with the trained checkpoint.

\paragraph{Scaling beyond the partition.}
Finally, the four-class study invites two outward steps: training on more
(eventually all 38) PatternNet categories to test whether the frozen-backbone
approach holds as the label space grows, and evaluating cross-dataset
transfer (e.g.\ on AID or NWPU-RESISC45 residential classes) to measure the
domain gap our single-source benchmark cannot reveal. Remote-sensing-specific
pretrained backbones would be the natural comparison point there,
substituting in-domain pretraining for ImageNet's.

\subsection{Reproduction Instructions}

All results in this report can be regenerated from the repository root.
The dataset directories are expected under \texttt{dataset/} (override with the
\texttt{CSC3109\_DATA\_DIR} environment variable).

\begin{verbatim}
# environment
pip install -r requirements.txt

# verify the shared-pipeline contract
pytest

# reproduce a final run (identical form for custom_cnn,
# resnet50, efficientnet_b0, mobilenetv2, ViT)
python train.py --model resnet50 --run-name resnet50 \
    --epochs 32 --patience 20 --batch-size 16 \
    --run-type final --evaluate-held-out
\end{verbatim}

Each run writes \texttt{results/<run>\_run.json} (metadata: seed, git
commit, split counts, parameters, best epoch),
\texttt{<run>\_history.json} (per-epoch curves),
\texttt{<run>\_tuning.json} and \texttt{<run>.json} (fixed-schema metrics on
the tuning and held-out sets), and the corresponding confusion-matrix and
training-curve figures. The shared \texttt{set\_seed()} seeds the random number
generators and requests deterministic TensorFlow kernels. This supports
repeatability under the recorded environment, but exact numerical equivalence
across reruns or machines is not claimed; TensorFlow 2.21.0 was used for all
final runs.
